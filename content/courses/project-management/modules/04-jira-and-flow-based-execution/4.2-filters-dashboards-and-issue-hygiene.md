# 4.2 Filters, dashboards and issue hygiene

> **Lesson plan** · 90 minutes — Read and discuss 25 min · Worked example 10 min · Hands-on lab 40 min · Quiz and reflection 15 min.

## Learning objectives

By the end of this lesson you can:

- Build reviewable Jira queries and dashboards without confusing missing data with healthy status.
- Produce a reviewable filter catalogue and board quality audit using the supplied practice case.
- Explain one limitation, one verification check and the next decision the evidence supports.

## Opening scenario

The coordinator shares a dashboard with zero overdue items. It looks reassuring until someone notices the filter excludes unassigned work and several records have no due date. A correct-looking chart can conceal a faulty selection rule.

The running organisation, Namma Campus Services, is fictional. All dates, costs, workloads and stakeholders in these exercises are synthetic. Work with role names rather than real student details. The case is deliberately small enough to model in a spreadsheet, but its approval, scheduling and communication problems resemble those encountered in entry-level coordination roles.

Write your initial recommendation before analysing the case. Keep it for comparison after the lab: what did the evidence change, and why?

## Core ideas

### 1. Query the decision, not the whole database

Start with a question: which active pilot items are overdue, which are unassigned, and which are waiting for review? Jira Query Language can combine project, status, due date and assignee fields, though field availability and names depend on configuration. Save each filter with its purpose, owner and expected scope. Test it against a few known records before relying on a dashboard.

### 2. Missing fields need separate checks

An item without a due date will not necessarily appear in a due-date comparison. Empty owner, absent acceptance criteria and stale status can be quality defects even when no deadline is technically missed. Create complementary data-hygiene checks rather than pretending one filter answers every question. Define who corrects records and how often. A query returning zero can mean no matching work, incorrect logic, insufficient permissions or incomplete data.

### 3. Dashboards support a conversation

A useful dashboard pairs a small set of measures with decisions and named owners. Show open blockers, ageing review work and milestone risk, not only total cards completed. Access permissions affect what each viewer can see; verify the intended audience’s view. Do not publish individual rankings from raw ticket counts. One complex incident and one minor text change are not equivalent units of effort or value.

## Worked example

A conceptual JQL filter is `project = PILOT AND statusCategory != Done AND due < now() ORDER BY due ASC`. Add separate checks such as `project = PILOT AND assignee IS EMPTY` and `project = PILOT AND due IS EMPTY`. Verify the project key and supported fields on the local site. A six-item fixture with two overdue, one undated and one unassigned item should produce predictable sets before publication.

### Reproduce before interpreting

Recreate the example from its inputs. Label units, show formulas or decision rules and keep an unchanged source copy. Change one assumption and identify which conclusion changes. Check one calculation or classification manually.

Test a relevant edge case: a missing date, zero denominator, incomplete observation or absent approval. Unknown information is not automatically zero or permission to invent a replacement. Record how the uncertainty affects your recommendation.

## Try it now

In pairs, explain the worked example without reading it aloud. The reviewer asks, “What evidence would change this recommendation?” Name the specific record, owner or observation you would request and how it could affect the decision. Swap roles and compare answers.

## Hands-on lab: filter catalogue and board quality audit (40 min)

Use the fictional case in this lesson. Do not contact real employees, candidates, customers or suppliers for these exercises. A spreadsheet, document and paper sketches are sufficient; named software is a convenience, not a requirement for marks.

1. Create six fictional issues with known due dates, owners and statuses.

2. Write three filters for overdue active work, missing ownership and missing due dates.

3. Predict which records each query should return, then compare with Jira or manual filtering.

4. Design a three-panel dashboard with an action owner and refresh cadence per panel.

5. Write a caveat explaining permissions and missing fields so a zero count is not overclaimed.

**Deliverable:** submit your filter catalogue and board quality audit, an assumptions note and a short recommendation. Use a descriptive filename containing the lesson number, your learner identifier and a revision number. Include the case period, units, source label “synthetic classroom case”, author and review date inside the artefact, not only in its filename.

### Lab review and acceptance

Reserve eight lab minutes for partner review. Trace one conclusion to its input, reproduce a calculation or classification and identify a possible misunderstanding. Keep the review comment and your correction or explanation in a two-column change log.

| Acceptance check | Evidence to leave in the submission |
| --- | --- |
| Scope is explicit | The question being answered and what is outside the exercise |
| Work can be reproduced | Source values, rules or formulas, and a manual check |
| Recommendation is actionable | Named role, next action and review trigger |
| Uncertainty is visible | An assumption and the effect if it proves false |
| Sharing is appropriate | Synthetic-data label and removal of unnecessary identifiers |

Working alone? Reopen the file as a reviewer. Check the version, evidence basis and distinction between observed facts and proposed actions.

## Common mistakes

- Interpreting zero results as proof that work is healthy.
- Using one overdue filter as a complete data-quality audit.
- Ranking staff using raw ticket counts.

Do not improve the appearance of a result by removing inconvenient records or changing an agreed definition halfway through the exercise. If the rule is wrong, propose a revision and show both versions. The goal is a defensible decision, not a perfect-looking chart or an artificially green status.

## Key takeaways

- **Query the decision, not the whole database:** Start with a question: which active pilot items are overdue, which are unassigned, and which are waiting for review? Jira Query Language can combine project, status, due date and assignee fields, though field availability and names depend on configuration.
- **Missing fields need separate checks:** An item without a due date will not necessarily appear in a due-date comparison.
- **Dashboards support a conversation:** A useful dashboard pairs a small set of measures with decisions and named owners.
