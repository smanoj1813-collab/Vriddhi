# 6.2 The build sprint

> **Lesson plan** · 120 minutes — Read 30 · Lab 80 · Quiz 10

## Learning objectives

By the end of this lesson you will be able to:

- Scope an MVP into a one-week sprint with a prioritised backlog and a definition of done.
- Choose and combine the right no-code components — assistant, automation, app, content pipeline — for your product.
- Wire an AI feature safely: prompt, structured output, fallback, cost, privacy.
- Keep a build log that records decisions, blockers and evidence of individual contribution.
- Run a daily stand-up and a mid-sprint demo that keeps the team honest.

## Opening scenario

The Yelahanka team has five interview syntheses, a lean canvas and a big whiteboard of features. Their mentor gives them one hour to produce a backlog with exactly three items marked "must" for the week. Everything else goes to "later". They choose: (1) a Google Sheet where prices for three markets are entered each evening (by hand this week); (2) an automation that, at 6 am, drafts a Kannada message per crop from a fixed template and generates a voice note; (3) a WhatsApp broadcast list of ten growers who agreed to try it. Nothing else. On day three it works badly; on day five it works; by day seven six growers are replying with their own prices — which was never in the plan and becomes the product's best feature.

## Core ideas

### 1. Scoping: the backlog and the definition of done

Turn the MVP statement into a **backlog**: a list of user stories in the form *"As a [user], I can [do something] so that [benefit]."* Prioritise with MoSCoW:

- **Must** — without this there is no test of the riskiest assumption (maximum three for a one-week sprint).
- **Should** — valuable, but the test survives without it.
- **Could** — nice; only if time remains.
- **Won't (this sprint)** — recorded so nobody argues about it again.

Write a **definition of done** for each Must: "A grower on the list receives one Kannada voice note by 6:30 am naming yesterday's price for their crop at three markets, and the sheet logs that it was sent." If you cannot write the done statement, the story is not clear enough.

Ask an assistant to split each Must into tasks under two hours each and to flag hidden dependencies ("you need the WhatsApp opt-in before the broadcast works").

### 2. Choosing the architecture (no code required)

Most capstones are a combination of blocks you already know:

| Block | Use it for | Tools |
| --- | --- | --- |
| **Data store** | The records of your product | Google Sheets, Airtable, Glide/AppSheet tables |
| **Input** | How users or you enter data | Google Forms, app forms, a WhatsApp/Telegram message, an email inbox |
| **Automation** | Schedules, triggers, notifications, AI steps | Make, n8n, Zapier, Apps Script |
| **AI feature** | Classify, extract, summarise, draft, translate, converse, generate voice/image | Model API steps inside the automation; assistant builders; TTS tools |
| **Interface** | What users see | No-code app, WhatsApp/Telegram messages, a shared dashboard, a simple website (Canva Sites, Google Sites, a vibe-coded page), an assistant chat |
| **Knowledge** | Documents the product answers from | NotebookLM-style tools, assistant knowledge files |

Draw the architecture as boxes and arrows on one page, with the data that flows on each arrow. Mark personal data in red. This diagram goes in the capstone report and is where a privacy reviewer will look first.

Keep it boring. **A sheet, one automation and a broadcast list** beats an elaborate app that does not run on demo day.

### 3. Wiring the AI feature safely

Apply Lessons 5.3 and 5.5 with capstone rigour:

1. **Write the prompt as a specification**: role, inputs (named fields), output format (JSON or a template with slots), rules ("never invent a price; if a market's price is missing, say 'not available'"), examples (three), fallback ("if input is malformed, return status: 'needs_review'").
2. **Test the prompt in a chat first** with twenty realistic inputs, including malformed ones. Fix until it passes 19/20. Only then put it in the automation.
3. **Validate outputs** in the flow before they reach users: schema check, allowed values, length limits, banned content (prices outside a plausible range).
4. **Cost and quota**: estimate runs per day × cost per run; check free-tier limits; add a daily cap.
5. **Privacy**: minimise fields sent to the model; no names or phone numbers unless essential; note the data flow in the diagram; add a privacy notice to the sign-up (Lesson 6.3).
6. **Language quality**: for Kannada/Hindi/Tamil/Telugu outputs, have a native speaker review twenty samples; keep a list of fixed phrasings the model must reuse.
7. **Human checkpoint** for anything external until the test log earns trust — a "review before send" step that you can remove later.

### 4. The build log

A shared document, updated every working day, with entries like:

```text
Day 3 — Tue
Done: Automation drafts Kannada template from sheet (Priya). TTS voice chosen —
"voice B" preferred by 3/4 growers in audition (Arun).
Decisions: Dropped per-grower personalisation this sprint — template per crop
instead. Reason: time; personalisation is a Should.
Blockers: WhatsApp broadcast limited to 256 contacts and needs opt-in; fine for
pilot. Make free tier: 1,000 ops/month — we use ~40/day, OK.
Evidence: screenshot of first successful run; sample voice note (link).
Tomorrow: opt-in form live; first send to 3 team phones.
Time: Priya 2.5h, Arun 2h, Meera 1.5h (interviews synthesis).
```

The log is the evidence of individual contribution that the rubric requires, and the raw material for your report and pitch. It also protects the team from the "who did what" argument.

### 5. Sprint rhythm

- **Daily stand-up (10 min, standing, or a voice note each):** yesterday, today, blockers. No problem-solving in the stand-up; take it offline.
- **Mid-sprint demo (day 3–4):** show whatever runs to a mentor or another team. Ugly is fine; fake is not. Adjust the backlog.
- **Timeboxes:** if a task passes twice its estimate, stop, log it, and find a simpler route. Vibe-coded prototypes and manual "Wizard of Oz" steps are legitimate simplifications for a pilot.
- **Always be demo-able:** at the end of each day the product should run end to end, even if some steps are manual. Add features only in a way that keeps it running.

### 6. Using AI as a team member (properly)

- **Planning:** split stories, estimate, spot dependencies.
- **Building:** draft prompts, templates, sheet formulas, Apps Script snippets you can read and test, messages to users.
- **Reviewing:** paste your prompt, template or flow description and ask for failure modes; run a persona-panel critique of the user experience.
- **Documenting:** turn the build log into a first-draft report section — then edit for truth.

Rule: **any AI-generated artefact enters the product only after a named team member has tested it and logged that they did.** The capstone rubric checks this.

## Try it now

Take your MVP statement and write three Must stories with definitions of done. Ask an assistant to break each into tasks under two hours and to list three ways each could fail on demo day. Assign the tasks to named team members with the day they will be done.

## Hands-on lab: sprint day one (80 min)

1. **Backlog and done (15 min):** MoSCoW; three Musts with done statements; tasks assigned.
2. **Architecture diagram (10 min):** boxes, arrows, data on arrows, personal data in red; the AI feature marked.
3. **Data store and input (15 min):** create the sheet or tables with realistic sample data; the input form or channel.
4. **AI feature prompt (20 min):** write the specification; test in chat with twenty inputs including five malformed; record the pass rate; iterate to 19/20.
5. **First wiring (15 min):** the automation or app step that calls the AI feature on one real row; validation filter; output to a review tab. Screenshot the first run — success or failure — into the build log.
6. **Log and plan (5 min):** day-one entry; tomorrow's tasks; blockers raised to the facilitator.

**Deliverable:** backlog with done statements, architecture diagram, prompt specification with test results, first-run screenshot, day-one build log entry. The sprint continues through the week; Lesson 6.3 assumes a running MVP.

## Common mistakes

- **Five Musts.** Three, or it is not a sprint.
- **Building the interface before the data and the AI step work.** Pretty and empty.
- **Putting an untested prompt into an automation.** Test in chat with twenty inputs first.
- **A build log written on the last night.** It is a daily record or it is fiction.
- **Perfectionism about automation.** Manual steps behind the scenes are fine for a pilot; say so honestly in the report.

## Key takeaways

- Backlog with MoSCoW, three Musts, a definition of done for each, tasks under two hours.
- Architecture from blocks you know: data store, input, automation, AI feature, interface, knowledge; one-page diagram with data flows and personal data marked.
- AI feature: prompt as specification, tested in chat to 19/20, validated in the flow, capped in cost, data-minimised, language-reviewed, human checkpoint until trusted.
- Daily build log with decisions, blockers, evidence and hours — the team's proof of work.
- Stand-ups, a mid-sprint demo, timeboxes and "always demo-able" keep the sprint honest.

## Reflection journal

Write 120 words: *Which story did you cut, and how did it feel? What did your AI feature get wrong in the twenty-input test, and what rule fixed it?*
