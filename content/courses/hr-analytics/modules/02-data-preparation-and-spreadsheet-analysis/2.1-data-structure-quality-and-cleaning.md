# 2.1 Data structure, quality and cleaning

> **Lesson plan** · 90 minutes — Read and discuss 25 min · Worked example 10 min · Hands-on lab 40 min · Quiz and reflection 15 min.

## Learning objectives

By the end of this lesson you can:

- Preserve raw data, identify record keys and document cleaning decisions before calculating HR metrics.
- Produce a reviewable cleaned synthetic dataset and quality log using the supplied practice case.
- Explain one limitation, one verification check and the next decision the evidence supports.

## Opening scenario

The applicant file contains repeated application IDs, inconsistent department labels and mixed date formats. One row says an offer was accepted before it was issued. A dashboard built directly from this file would convert data-quality defects into management claims.

Namma People Services is a fictional organisation created for this course. All employee IDs, applications, costs, survey responses and workforce events are synthetic. The exercises model decisions an entry-level HR team might support, but they do not authorise live selection, dismissal, health inference or individual employee-risk scoring. Use the supplied practice records rather than collecting real personal data.

Write your initial recommendation before analysing the case. Keep it for comparison after the lab: what did the evidence change, and why?

## Core ideas

### 1. Understand the grain and key

The grain is what one row represents: an application, employee-month, interview event or requisition. Select a key appropriate to that grain. A candidate may legitimately have several application records; deleting rows by candidate ID alone can destroy valid activity. A duplicate application ID may be an exact repeat or conflicting versions. Investigate and record the rule used to retain, merge or quarantine records.

### 2. Preserve source and make changes traceable

Keep a read-only raw copy, a working table and a cleaning log. Standardise labels through an explicit mapping, trim unwanted spaces and parse dates using a declared format. Distinguish blanks from zero and “not applicable”. Never infer a sensitive personal characteristic from a name. If a record is impossible, quarantine it or request correction rather than inventing a plausible value to make the spreadsheet complete.

### 3. Check validity, completeness and reconciliation

Test unique keys, required fields, valid category values, chronological event order and totals before and after cleaning. A quality report should show counts of changed, excluded and unresolved rows. Reconcile distinct entities as well as row counts where necessary. A cleaned dataset can still have missing coverage; document limitations rather than calling it perfect. The goal is reproducibility, not a cosmetic absence of blanks.

## Worked example

A source has 52 rows. Two are exact repeated application records and one has an impossible acceptance date. Removing the exact repeats yields 50 distinct application records; quarantining the invalid record leaves 49 usable records for time-based analysis. Report all three counts. Do not claim 49 is the number of distinct candidates unless candidate IDs are separately deduplicated.

### Reproduce before interpreting

Recreate the example from its inputs. Label units, show formulas or decision rules and keep an unchanged source copy. Change one assumption and identify which conclusion changes. Check one calculation or classification manually.

Test a relevant edge case: a missing date, zero denominator, incomplete observation or absent approval. Unknown information is not automatically zero or permission to invent a replacement. Record how the uncertainty affects your recommendation.

## Try it now

In pairs, explain the worked example without reading it aloud. The reviewer asks, “What evidence would change this recommendation?” Name the specific record, owner or observation you would request and how it could affect the decision. Swap roles and compare answers.

## Hands-on lab: cleaned synthetic dataset and quality log (40 min)

Use the fictional case in this lesson. Do not contact real employees, candidates, customers or suppliers for these exercises. A spreadsheet, document and paper sketches are sufficient; named software is a convenience, not a requirement for marks.

1. Copy the synthetic practice table into raw and working tabs without changing raw.

2. Define application ID as the record key and identify exact versus conflicting duplicates.

3. Create mappings for department labels and declare an unambiguous date format.

4. Quarantine an impossible event sequence and record its effect on analysis denominators.

5. Produce a quality summary and reconcile raw, distinct and usable record counts.

**Deliverable:** submit your cleaned synthetic dataset and quality log, an assumptions note and a short recommendation. Use a descriptive filename containing the lesson number, your learner identifier and a revision number. Include the case period, units, source label “synthetic classroom case”, author and review date inside the artefact, not only in its filename.

### Lab review and acceptance

Reserve eight lab minutes for partner review. Trace one conclusion to its input, reproduce a calculation or classification and identify a possible misunderstanding. Keep the review comment and your correction or explanation in a two-column change log.

| Acceptance check | Evidence to leave in the submission |
| --- | --- |
| Scope is explicit | The question being answered and what is outside the exercise |
| Work can be reproduced | Source values, rules or formulas, and a manual check |
| Recommendation is actionable | Named role, next action and review trigger |
| Uncertainty is visible | An assumption and the effect if it proves false |
| Sharing is appropriate | Synthetic-data label and removal of unnecessary identifiers |

Working alone? Reopen the file as a reviewer. Check the version, evidence basis and distinction between observed facts and proposed actions.

## Common mistakes

- Deduplicating by a key that does not match the row grain.
- Replacing all blanks with zero.
- Hiding excluded records to make totals look consistent.

Do not improve the appearance of a result by removing inconvenient records or changing an agreed definition halfway through the exercise. If the rule is wrong, propose a revision and show both versions. The goal is a defensible decision, not a perfect-looking chart or an artificially green status.

## Key takeaways

- **Understand the grain and key:** The grain is what one row represents: an application, employee-month, interview event or requisition.
- **Preserve source and make changes traceable:** Keep a read-only raw copy, a working table and a cleaning log.
- **Check validity, completeness and reconciliation:** Test unique keys, required fields, valid category values, chronological event order and totals before and after cleaning.
