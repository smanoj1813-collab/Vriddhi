# 6.2 Build and quality-check a dashboard

> **Lesson plan** · 90 minutes — Read and discuss 25 min · Worked example 10 min · Hands-on lab 40 min · Quiz and reflection 15 min.

## Learning objectives

By the end of this lesson you can:

- Create an aggregate dashboard with tested filters, reproducible totals and safe sharing settings.
- Produce a reviewable working dashboard and QA checklist using the supplied practice case.
- Explain one limitation, one verification check and the next decision the evidence supports.

## Opening scenario

A spreadsheet dashboard looks correct until a department filter changes the numerator but leaves the denominator fixed. The resulting conversion rate is plausible enough to escape notice. Dashboard QA needs known test cases, not only a visual inspection.

Namma People Services is a fictional organisation created for this course. All employee IDs, applications, costs, survey responses and workforce events are synthetic. The exercises model decisions an entry-level HR team might support, but they do not authorise live selection, dismissal, health inference or individual employee-risk scoring. Use the supplied practice records rather than collecting real personal data.

Write your initial recommendation before analysing the case. Keep it for comparison after the lab: what did the evidence change, and why?

## Core ideas

### 1. Separate data, calculations and presentation

Use raw, cleaned, metric and dashboard layers so transformations are inspectable. A pivot or formula layer should produce the values displayed; avoid typing summary numbers directly into chart labels. Keep an Unknown group visible when data is incomplete. A refresh should not silently change definitions. Document how new rows are included and how dates are interpreted.

### 2. Test filters and totals deliberately

Check an unfiltered total, a single group, an empty selection and a combination of filters. Numerator and denominator must use compatible populations. Test duplicates, missing dates and late-arriving records. Compare key values to a manual calculation and reconcile summaries to detail. A dashboard with correct charts but incorrect filters is analytically wrong, even if it looks professional.

### 3. Share only the necessary layer

Use aggregate outputs for portfolio work and check access using the intended viewer role. Hidden spreadsheet tabs are not a security boundary if viewers can unhide or download them. Remove real identifiers rather than relying on visual hiding. Excel, Google Sheets and an offline equivalent are acceptable; an optional BI tool can be used only if access and data handling are appropriate. No paid publication feature is required.

## Worked example

A department has 8 acceptances from 10 offers, while the organisation has 30 from 40. The department rate is 80%, not 8/40 = 20%. A filter test should assert both counts change together. For an empty department, display “not applicable, n=0”. Before sharing, inspect whether the exported file contains underlying rows that the audience should not receive.

### Reproduce before interpreting

Recreate the example from its inputs. Label units, show formulas or decision rules and keep an unchanged source copy. Change one assumption and identify which conclusion changes. Check one calculation or classification manually.

Test a relevant edge case: a missing date, zero denominator, incomplete observation or absent approval. Unknown information is not automatically zero or permission to invent a replacement. Record how the uncertainty affects your recommendation.

## Try it now

In pairs, explain the worked example without reading it aloud. The reviewer asks, “What evidence would change this recommendation?” Name the specific record, owner or observation you would request and how it could affect the decision. Swap roles and compare answers.

## Hands-on lab: working dashboard and QA checklist (40 min)

Use the fictional case in this lesson. Do not contact real employees, candidates, customers or suppliers for these exercises. A spreadsheet, document and paper sketches are sufficient; named software is a convenience, not a requirement for marks.

1. Build three dashboard measures from the cleaned synthetic workbook.

2. Create a QA table with expected outputs for all, single-group and empty filters.

3. Test the eight-of-ten example and verify denominator behaviour.

4. Record refresh steps and compare two outputs to manual calculations.

5. Export an aggregate-only portfolio view and check that hidden raw data is not inadvertently included.

**Deliverable:** submit your working dashboard and QA checklist, an assumptions note and a short recommendation. Use a descriptive filename containing the lesson number, your learner identifier and a revision number. Include the case period, units, source label “synthetic classroom case”, author and review date inside the artefact, not only in its filename.

### Lab review and acceptance

Reserve eight lab minutes for partner review. Trace one conclusion to its input, reproduce a calculation or classification and identify a possible misunderstanding. Keep the review comment and your correction or explanation in a two-column change log.

| Acceptance check | Evidence to leave in the submission |
| --- | --- |
| Scope is explicit | The question being answered and what is outside the exercise |
| Work can be reproduced | Source values, rules or formulas, and a manual check |
| Recommendation is actionable | Named role, next action and review trigger |
| Uncertainty is visible | An assumption and the effect if it proves false |
| Sharing is appropriate | Synthetic-data label and removal of unnecessary identifiers |

Working alone? Reopen the file as a reviewer. Check the version, evidence basis and distinction between observed facts and proposed actions.

## Common mistakes

- Filtering only the numerator.
- Treating hidden tabs as secure storage.
- Manually typing chart values that drift from the source.

Do not improve the appearance of a result by removing inconvenient records or changing an agreed definition halfway through the exercise. If the rule is wrong, propose a revision and show both versions. The goal is a defensible decision, not a perfect-looking chart or an artificially green status.

## Key takeaways

- **Separate data, calculations and presentation:** Use raw, cleaned, metric and dashboard layers so transformations are inspectable.
- **Test filters and totals deliberately:** Check an unfiltered total, a single group, an empty selection and a combination of filters.
- **Share only the necessary layer:** Use aggregate outputs for portfolio work and check access using the intended viewer role.

## Reflection journal

2. Which assumption has the greatest effect on your recommendation, and how would you test it before a real decision?
3. How would you explain this work in a two-minute interview for HR Executive without claiming a classroom simulation was paid experience?
